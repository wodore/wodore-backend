# Proposal: add-api-date-versioning

## Why

The Wodore API (`/v1/`) is consumed by a Capacitor mobile app that stays installed for months. Breaking API changes today either break old clients or force a `/v2/` URL bump for every incompatibility. We want Stripe-style evolution: one codebase running only the newest logic, while older clients keep receiving the response shape they were built against until their pinned version is sunset — with machine-readable warning before it stops working.

## What Changes

- **Date-based API versions inside `/v1/`**: clients select a contract version (`YYYY-MM-DD`) via the `Api-Version` request header or the `api_version` query parameter. `/v1/` remains the major version. No version given → latest.
- **Version registry** in a new Django app `server/apps/apiversions/`: every future breaking change is a `VersionChange` entry (date, description, request/response transforms keyed by operationId). This change ships the registry and transform pipeline with **zero production transforms** — the first real breaking change is its own follow-up change.
- **Deprecation lifecycle**: deprecated versions (and the already-deprecated `/v1/huts/bookings*` endpoints) send `Deprecation` (RFC 9745), `Sunset` (RFC 8594) and `Link; rel="deprecation"` headers; versions past sunset return `410 Gone`.
- **`/v1/version` extended** (additive) with an `api` block: current, default and supported versions with status and sunset dates.
- **OpenAPI snapshots per version**, generated by `manage.py api_snapshot` and committed; `/v1/openapi.json?api_version=` serves the matching snapshot; docs get a version switcher.
- **Caching correctness**: the resolved version participates in ETag key material and `Vary: Api-Version` is set on header-resolved responses (the existing `huts.geojson` ETag is query-keyed and would otherwise 304 across versions).
- **Separate API changelog** (`API_CHANGELOG.md`) via git-cliff (`cliff-api.toml`) from `api:*` PR labels and `api/YYYY-MM-DD` tags; backend `CHANGELOG.md` unchanged.
- **BREAKING (process only)**: from now on, breaking changes require a new `VersionChange` + snapshot + `api:breaking`-labeled PR. No breaking change for pinned clients.

## Capabilities

### New Capabilities

- `api-versioning`: Version selection and resolution, scope, transform pipeline, deprecation/sunset lifecycle for versions and endpoints, version discovery via `/v1/version`, CORS access to version headers, caching correctness, registry integrity validation.
- `api-docs`: Per-version OpenAPI snapshots, version-addressable schema serving, docs version switching, contract tests against snapshots.
- `api-changelog`: Separate git-cliff-generated API changelog and the breaking-changes-require-a-version process gate.

### Modified Capabilities

(none — no existing spec covers API shape evolution)

## Impact

- **New code**: `server/apps/apiversions/` (Django app: registry, resolver, middleware, renderer, snapshot command); `cliff-api.toml`.
- **Modified code**: `server/apps/api/api_v1.py` (renderer + operation wrapping), `server/apps/utils/api.py` (`/v1/version` api block), `server/apps/huts/api/_hut.py` + `server/apps/availability/api.py` (explicit transform helper call + ETag version keying for the two direct-write GeoJSON endpoints), `server/settings/components/common.py` (CORS allow/expose headers, middleware, INSTALLED_APPS), `_booking.py` (Sunset date for bookings endpoints).
- **CI**: snapshot presence check, optional `api:breaking` label ↔ registry check.
- **Clients** (out of scope here): Capacitor app pins `Api-Version` via Axios interceptor; MapLibre layer URLs may pin via `?api_version=`.
- **Dependencies**: none new (no versioning library; concept borrowed from Stripe/Cadwyn).

## Requirements
### Requirement: Schema-derived query specs

The system SHALL provide a derivation function that converts a pydantic response schema into a django-readers spec, where plain fields become field entries, nested models mapped to model relations become relationship entries, and an optional sparse `fields[TYPE]` selection restricts the spec to the requested subset.

#### Scenario: Plain schema derives field-only spec

- **WHEN** `spec_from_schema` is called with a schema whose fields all map to model fields
- **THEN** the returned spec contains exactly those field entries and the processed queryset selects only those columns

#### Scenario: Nested model derives relationship entry

- **WHEN** a schema field's type is a nested pydantic model whose name maps to a model relation (FK or reverse)
- **THEN** the spec contains a relationship entry for that relation with the nested model's fields as its subtree

#### Scenario: Sparse fieldset restricts the spec

- **WHEN** a `fields[TYPE]` selection is supplied alongside the schema
- **THEN** the derived spec includes only the selected fields (and their nested subtrees), and unselected relations are neither selected nor prefetched

#### Scenario: Explicit overrides win over derivation

- **WHEN** `spec_overrides` supplies a custom reader pair for a field
- **THEN** the derived spec uses that pair verbatim instead of the generated entry

### Requirement: Query-count regression tests

Every endpoint converted to derived specs SHALL have a test pinning its query count; a change that introduces an additional query (N+1) SHALL fail the test suite.

#### Scenario: Converted endpoint query count stays pinned

- **WHEN** the test suite runs against an endpoint using a derived spec
- **THEN** the request executes at most the query count recorded when the endpoint was converted

### Requirement: Hot-path benchmark gate

The system SHALL provide a benchmark harness comparing hand-tuned and readers-generated implementations for `search_huts`, `huts.geojson`, and geo search/nearby endpoints; a hot path SHALL only be converted when p50 latency is within noise (±5%) and p95 is not worse than the hand-tuned implementation.

#### Scenario: Hot path at parity may be converted

- **WHEN** the harness reports p50 within ±5% and p95 not worse for the readers-generated implementation
- **THEN** the hot path may be converted to derived specs

#### Scenario: Hot path slower than hand-tuned stays annotated

- **WHEN** the harness reports the readers-generated implementation slower than the threshold
- **THEN** the hot path keeps its `JSONBAgg` annotations and the decision is documented in the code

### Requirement: Computed fields as reader pairs

Computed and aggregated fields (distance, availability aggregates, JSONB collections) SHALL be expressed as explicit django-readers reader pairs, not generated by the derivation function.

#### Scenario: Annotation-backed field uses its reader pair

- **WHEN** a schema field is backed by a custom annotation (e.g. hut sources aggregation)
- **THEN** its spec entry is the registered reader pair and the annotation SQL is unchanged from the hand-tuned implementation
